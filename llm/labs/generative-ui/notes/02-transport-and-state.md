# 전송, 상태, 상호작용

화면을 무엇으로 기술할지와 별개로, 그것을 어떻게 실어 나르고 어떻게 살아 있게
유지할지가 따로 문제가 된다.

## 왜 스트리밍이 필요한가

모델의 응답은 한 번에 나오지 않는다. 화면을 다 만들 때까지 기다렸다가 그리면
사용자는 빈 화면을 오래 본다. 그래서 오는 대로 그린다.

여기서 두 가지가 걸린다.

- **덜 온 코드는 그릴 수 없다.** 닫히지 않은 태그, 잘린 JSON은 그대로 넣으면 깨진다
- **스크립트를 언제 돌릴지 정해야 한다.** 그리는 도중에 실행되면 아직 없는 요소를 찾는다

인라인 위젯 방식이 "스크립트는 스트리밍이 끝난 뒤 실행된다"고 규정하는 것이
두 번째에 대한 답이다. 첫 번째는 완성된 조각 단위로만 넘기거나, 조각이 완성될
때까지 버퍼에 모으는 방식으로 처리한다.

## 조각 전달과 렌더링 방식은 별개다

화면 조각을 내려보내는 것과 서버 렌더링은 관계가 없다. HTML 문자열을 받아 문서로
만드는 일은 브라우저에서 하므로, 서버 렌더링 없이도 된다.

무엇을 조각으로 내리느냐에 따라서만 갈린다.

| 내려보내는 것 | 서버 렌더링 |
| --- | --- |
| HTML 문자열 | 필요 없다. 받아서 넣으면 된다 |
| 선언적 기술 | 필요 없다. 클라이언트가 컴포넌트로 바꾼다 |
| 서버 컴포넌트 트리 | 필요하다. 서버에서 렌더해 직렬화한다 |

실제 제약은 렌더링 위치가 아니라 격리다. 받은 HTML 을 같은 문서에 그대로 넣으면
그 안의 스크립트가 부모 화면에 접근한다. 그래서 별도 문서로 격리하고 정책을 건다.

## 서버 렌더링이 유리해지는 경우

대화 중 실시간으로 나오는 화면에는 이점이 없다. 브라우저가 이미 떠 있고 스트림으로
받는 상황이므로 서버가 미리 렌더할 것이 없다.

생성된 화면에 주소가 붙어 문서로 남는 순간 달라진다.

| 이점 | 내용 |
| --- | --- |
| 공유와 재방문 | 링크를 열었을 때 첫 표시가 빠르고 스크립트 없이도 보인다 |
| 미리보기 | 링크를 붙였을 때 미리보기가 나오려면 서버가 내용을 줘야 한다 |
| 번들 크기 | 컴포넌트 종류가 많을 때 쓰인 것만 내려보낼 수 있다 |
| 비밀 유지 | 서버 쪽 자료나 키를 써서 그리고 결과만 내려보낸다 |
| 왕복 감소 | 도구 실행과 렌더링이 같은 서버에서 이어진다 |

일회성 대화 화면에는 이점이 없고, 산출물이 문서로 남아 공유되는 구조에는 있다.

## 이벤트로 나누어 보내기

전송 규격은 오가는 것을 종류별로 나눈다. 대략 다음과 같이 갈린다.

| 종류 | 내용 |
| --- | --- |
| 글자 조각 | 응답 본문이 조금씩 |
| 도구 호출 | 어떤 도구를 어떤 인자로 부르는지, 그 결과 |
| 상태 변화 | 전체가 아니라 바뀐 부분만 |
| 수명 주기 | 시작, 종료, 오류 |
| 사용자 정의 | 위 분류에 안 들어가는 것 |

상태를 통째로 다시 보내지 않고 **바뀐 부분만** 보내는 것이 핵심이다. 화면이 긴
목록을 들고 있을 때 전체를 다시 그리지 않으려면 이 구분이 필요하다.

전송 수단 자체는 새로운 것을 쓰지 않는다. 서버가 밀어 주는 방식이거나 양방향
소켓이며, 규격은 그 위에 얹는 약속이다.

## 상호작용을 되돌리는 통로

화면이 표시 장치에 머물면 문제가 없지만, 사용자가 그 안에서 무언가를 누르면
그 사실을 에이전트가 알아야 한다. 통로는 대체로 셋 중 하나다.

| 방식 | 설명 |
| --- | --- |
| 대화로 되돌리기 | 누른 결과를 사용자 발화처럼 대화에 넣는다. 가장 단순하다 |
| 도구 결과로 되돌리기 | 진행 중인 도구 호출의 응답으로 넣는다. 흐름이 끊기지 않는다 |
| 상태 갱신으로 되돌리기 | 공유 상태를 고치고 그 변화를 양쪽이 본다 |

첫 번째는 구현이 쉽지만 대화 기록이 지저분해진다. 두 번째는 자연스럽지만 도구가
사용자 응답을 기다릴 수 있는 구조여야 한다.

## 다시 열었을 때

대화를 닫았다 다시 열면 화면을 복원해야 한다. 여기서 방식별로 차이가 크다.

| 방식 | 복원 |
| --- | --- |
| 선언적 기술 | 기술 자체가 데이터이므로 그대로 다시 그린다 |
| 코드 생성 | 코드를 저장해 두었다가 다시 실행한다 |
| 슬롯 주입 | 화면이 다시 열릴 때 다시 전달해야 한다 |

세 번째가 가장 까다롭다. 살아 있는 실행 상태에 얹히는 방식이라, 대상이 사라지면
다시 붙여 줄 주체가 필요하다. dsh가 "이미 실행 중인 것을 다시 실행하면 실패시키지
않고 다시 전달한다"고 규정한 것이 이 문제에 대한 답이다.

한 걸음 더 들어가면, 복원해야 할 것이 화면만이 아니다. 사용자가 그 안에서 입력해
둔 값, 열어 둔 탭, 스크롤 위치도 있다. 이것들은 대체로 복원 대상에서 빠진다.

## 상태를 누가 들고 있는가

세 가지 선택지가 있고 각각 대가가 다르다.

| 보관 위치 | 장점 | 대가 |
| --- | --- | --- |
| 화면 쪽 | 반응이 빠르다 | 새로 고치면 사라진다 |
| 서버 쪽 | 복원과 공유가 쉽다 | 오갈 것이 늘어난다 |
| 대화 기록 안 | 모델이 함께 본다 | 기록이 커지고 토큰을 먹는다 |

세 번째는 모델이 화면 상태를 인지해야 할 때만 고른다. 사용자가 표에서 무엇을
선택했는지 모델이 알아야 다음 답을 낼 수 있다면 여기에 둘 수밖에 없다.
