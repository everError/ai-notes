# 용어 정리

이 분야는 서로 다른 세 가지가 한 이름으로 불려 혼란이 크다. 먼저 축을 나눈다.

## 세 가지는 층이 다르다

| 구분 | 무엇을 정하는가 | 예 |
| --- | --- | --- |
| 서버 주도 UI | 화면을 무엇으로 기술할 것인가 | A2UI, 자체 정의한 `{type, props}` |
| 생성형 UI | 화면을 누가 만들 것인가 | Artifacts, v0 |
| 전송 규격 | 화면 정보를 어떻게 실어 나를 것인가 | AG-UI |

서로 대체 관계가 아니다. 전송 규격 위에 서버 주도 방식의 화면 기술을 실어 나를 수
있고, 생성형으로 만든 코드를 같은 경로로 보낼 수도 있다.

## 서버 주도 UI

서버가 미리 정의된 컴포넌트를 선언적으로 기술해 내려보내고 클라이언트가 그린다.
모바일 앱을 배포 없이 바꾸려는 목적으로 오래 쓰여 온 방식이며, 에이전트가 그
기술을 만들어 낸다는 점만 새롭다.

컴포넌트 목록이 미리 정해져 있으므로 목록 밖의 화면은 표현할 수 없다. 대신
코드를 실행하지 않으므로 안전하고, 같은 기술을 웹과 모바일에서 함께 쓸 수 있다.

## 생성형 UI

모델이 화면 자체를 만들어 낸다. 두 갈래로 나뉘며 성격이 크게 다르다.

| 갈래 | 모델이 내보내는 것 | 표현 범위 |
| --- | --- | --- |
| 컴포넌트 선택형 | 어떤 컴포넌트를 어떤 값으로 쓸지 | 준비된 목록 안 |
| 코드 생성형 | 화면 코드 자체 | 제한 없음 |

컴포넌트 선택형은 결국 서버 주도 UI와 같은 자리에 선다. 트리거가 도구 호출이라는
점만 다르다. 이름은 생성형이지만 실제로 생성하는 것은 값뿐이다.

## 전송 규격

에이전트 실행부와 화면 사이에 오가는 이벤트를 표준화한다. 글자 조각, 도구 호출,
상태 변화, 수명 주기 같은 것들이 대상이다. 화면을 무엇으로 기술할지는 정하지 않는다.

## 판단이 갈리는 지점

무엇을 고를지는 다음 질문으로 갈린다.

1. 화면의 종류가 미리 정해지는가, 요청마다 달라지는가
2. 모델이 만든 코드를 실행해도 되는가
3. 웹 외의 플랫폼에서도 같은 화면을 그려야 하는가

1번이 정해져 있고 2번이 안 되면 서버 주도 UI가 맞다. 1번이 열려 있으면 코드
생성형 외에 선택지가 없고, 그 순간 격리가 가장 큰 문제가 된다.
