# 기법 여섯 가지

실제로 쓰이는 방식을 구조와 대가 중심으로 정리한다.

## 1. 코드 생성 + 격리 문서

모델이 화면 코드를 통째로 만들고, 격리된 프레임에서 문서 하나로 띄운다.

**구조**

```
모델 → HTML/CSS/JS 전체 생성 → 격리 프레임에 문서로 적재
```

**제약이 표현을 규정한다.** 외부 요청을 막는 정책이 걸리므로 스타일과 스크립트를
전부 안에 넣어야 하고, 이미지도 데이터 URI로 박아 넣는다. 바깥 서버로 나가는
요청, 원격 스크립트, 소켓 연결이 모두 차단된다.

**적합한 곳** — 사용자가 요청한 산출물. 보고서, 대시보드, 목업, 계산기처럼 한 번
만들어 그대로 보는 것.

**대가**

- 코드를 통째로 생성하므로 토큰이 많이 든다
- 실행 전에 옳은지 검증할 방법이 없다
- 매번 다르게 만들어지므로 화면 일관성이 없다
- 격리를 뚫는 시도에 노출된다

## 2. 대화 안 인라인 위젯

답변 흐름 중간에 조각을 그린다. 문서 하나를 통째로 띄우는 것이 아니라 본문만 넘긴다.

**구조**

```
모델 → SVG 또는 HTML 조각 → 답변 옆에 삽입
```

**세부 규칙이 1번과 다르다.**

- 문서 뼈대(`html`, `head`, `body`)를 넣지 않는다. 본문만 넘긴다
- 배경을 투명하게 두고 바깥 여백을 넣지 않는다. 호스트 화면에 얹히기 때문이다
- 색은 호스트가 정의한 변수를 쓴다. 밝은 화면과 어두운 화면을 함께 따라가야 한다
- 스크립트는 글자 스트리밍이 끝난 뒤 실행된다. 그리는 도중에 돌면 안 된다

**양방향이 가능하다.** 위젯에서 사용자가 누른 것을 대화로 되돌려 보내는 통로를
호스트가 제공하기도 한다. 이때 위젯은 표시 장치가 아니라 입력 장치가 된다.

**적합한 곳** — 설명을 돕는 그림, 비교표, 작은 상호작용. 답변의 일부로 읽히는 것.

## 3. 슬롯 주입

호스트 앱이 미리 자리를 열어 두고, 플러그인이 그 자리에 컴포넌트를 꽂는다.

**구조**

```
플러그인 = 호스트 절반 + 브라우저 절반
브라우저 절반 → 열려 있는 모든 화면으로 전달 → 선언된 슬롯에 등록
```

**슬롯 목록이 계약이다.** 어떤 자리가 있는지, 그 자리에 꽂히는 컴포넌트가 어떤
값을 받는지가 미리 문서로 정리된다. 이 목록이 없으면 무엇을 만들 수 있는지 알 수
없으므로, 목록 자체를 코드에서 생성해 최신 상태로 유지하는 구조를 두기도 한다.

**적합한 곳** — 도구 자체를 확장하는 경우. 사용자에게 보여줄 산출물이 아니라
에이전트 화면의 기능을 늘리는 것.

**대가** — 준비된 자리 안에서만 가능하다. 대신 호스트 화면과 이질감이 없다.

## 4. 선언적 화면 기술

컴포넌트 목록을 정해 두고, 화면을 그 조합의 트리로 기술해 내려보낸다.

**구조**

```
{ type: "data-table", props: { columns: [...], rows: [...] } }
```

코드를 실행하지 않으므로 격리 문제가 없다. 같은 기술을 웹과 모바일에서 함께 쓸
수 있다는 것이 큰 장점이다.

**대가** — 목록 밖은 표현할 수 없다. 새 화면이 필요할 때마다 클라이언트를 고쳐야
하므로, 배포 없이 화면을 바꾼다는 원래 목적과 부분적으로 충돌한다.

## 5. 도구 호출과 컴포넌트 대응

모델은 도구를 부르기만 하고, 화면 쪽이 도구 이름과 결과 형태를 보고 컴포넌트를
고른다.

**구조**

```
모델 → 도구 호출 → 결과 형태 판별(코드) → 대응되는 컴포넌트로 렌더
```

모델은 화면을 전혀 모른다. 화면 결정이 전부 코드에 있으므로 예측 가능하고 시험하기
쉽다. 실질적으로 4번과 같은 자리이며, 무엇이 대응을 촉발하는지만 다르다.

**적합한 곳** — 도구 결과의 표시 방식이 정해져 있는 경우. 검색 결과, 표, 지도.

## 6. 도구 결과에 화면을 실어 보내기

도구를 제공하는 쪽이 결과와 함께 화면 조각을 돌려준다. 도구 서버가 자기 결과를
어떻게 보여줄지 스스로 정하는 방식이다.

**적합한 곳** — 도구 제공자와 화면 제작자가 다른 조직일 때. 도구를 붙이면 화면도
함께 따라온다.

**대가** — 도구 서버가 보낸 것을 호스트가 그리게 되므로 신뢰 경계가 늘어난다.
1번과 같은 격리가 필요하다.

## 실제로는 섞어 쓴다

코딩 에이전트를 보면 두 갈래가 공존한다.

| 대상 | 방식 |
| --- | --- |
| 사용자가 요청한 산출물 | 1, 2 (코드 생성) |
| 에이전트 동작 표시 (변경 내역, 할 일, 승인 창) | 3, 4, 5 (고정 컴포넌트) |

임의의 요청은 목록으로 덮을 수 없으니 코드를 만들고, 반복되는 표시는 고정한다.
한 제품 안에서 두 방식을 나누는 기준이 이것이다.
