# 격리와 위험

모델이 만든 코드를 화면에 띄운다는 것은 검증되지 않은 코드를 사용자 브라우저에서
실행한다는 뜻이다. 이 방식의 가장 큰 비용이 여기에 있다.

## 왜 특별히 위험한가

보통의 웹 애플리케이션은 개발자가 쓴 코드를 배포한다. 검토와 시험을 거친다.
생성형 화면은 그 과정이 없다. 그리고 그 코드를 만드는 재료에는 다음이 섞인다.

- 사용자가 입력한 문장
- 도구가 가져온 외부 문서와 웹 내용
- 다른 도구 서버가 돌려준 값

즉 외부에서 들어온 내용이 실행되는 코드로 이어지는 경로가 열려 있다.

## 격리 수단

| 수단 | 막는 것 |
| --- | --- |
| 격리 프레임 | 부모 화면의 문서와 저장소 접근 |
| 콘텐츠 보안 정책 | 외부 서버로 나가는 요청, 원격 스크립트 |
| 자족성 요구 | 스타일과 이미지까지 안에 넣게 해 외부 의존을 없앰 |
| 내려받기 차단 | 화면이 스스로 시작하는 파일 저장 |
| 별도 실행 영역 | 호스트 전역에 대한 접근 |

앞선 dsh 조사에서 확인한 것은 실행 영역 격리가 **보안 경계가 아니라고 문서가
명시**한다는 점이다. 전역을 가리고 표준 기능을 대체 서비스로 돌려 놓지만, 호스트
쪽 보조 함수를 통한 탈출이 가능하다고 적혀 있다. 그래서 그 기능을 셸 접근과 같은
수준으로 취급하라고 한다.

이것이 일반적인 상태다. 격리는 실수를 줄이지만 악의를 막지는 못한다.

## 코드를 실행하지 않는 선택

선언적 기술 방식이 다시 검토되는 이유가 여기에 있다. 컴포넌트 목록을 벗어날 수
없다는 제약이, 그대로 안전 보장이 된다. 표현력을 포기하고 검증 가능성을 얻는
교환이다.

**판단 기준은 신뢰 경계다.** 화면을 만드는 재료가 전부 내부에서 온 것이라면 코드
생성을 써도 된다. 외부에서 들어온 내용이 섞인다면 선언적 방식이 맞다.

## 코드 실행 외의 위험

격리를 완벽히 해도 남는 것들이 있다. 실행 문제가 아니라 표시 문제이기 때문이다.

| 위험 | 내용 |
| --- | --- |
| 사람을 속이는 화면 | 실제 서비스처럼 보이는 로그인 창을 그려 입력을 유도 |
| 거짓 기록 | 영수증, 증명서, 명세서처럼 보이는 것을 만들어 냄 |
| 가짜 출처 | 실재하는 기관이나 사람의 이름과 표시를 붙임 |
| 잘못된 확신 | 그럴듯한 도표가 근거 없는 수치를 사실처럼 보이게 함 |

마지막이 특히 다루기 어렵다. 같은 값이라도 글로 적으면 의심받는데 도표로 그리면
검증된 것처럼 읽힌다. 화면이 신뢰도를 올려 주는 효과가 있어서, 근거 없는 내용일수록
피해가 커진다.

## 정리

| 질문 | 답이 정하는 것 |
| --- | --- |
| 화면 재료에 외부 내용이 섞이는가 | 코드 생성 여부 |
| 사용자가 이 화면을 공유하거나 저장하는가 | 오인 위험의 크기 |
| 화면이 값을 입력받는가 | 자격 증명 관련 검토 필요 |
| 화면이 밖으로 요청을 보내는가 | 정책으로 막을지 허용할지 |

코드 생성 방식을 고를 때는 격리를 붙이는 것으로 끝나지 않는다. 무엇을 그리게 할
것인지에 대한 규칙이 함께 있어야 한다.
