# 요청 하나가 처리되는 흐름

플러그인이 언제 도는지, 모델이 무엇을 정하는지를 정리한다.

## 방향을 먼저 잡는다

플러그인이 모델을 굴린다. 모델이 플러그인을 굴리는 것이 아니다.
모델은 플러그인의 존재를 모르며, 플러그인 안에 들어 있는 부품에 가깝다.

| | 정하는 주체 | 시점 |
| --- | --- | --- |
| 플러그인 | 사람이 설정으로 | 실행할 때 한 번 |
| 도구 | 모델이 | 매 턴 |

모델이 보는 것은 도구 목록뿐이다. 플러그인 이름은 모델에게 전달되지 않는다.

## 흐름

**요청 준비**

1. `dsh-session` 이 메시지를 기록하고 `dsh-session-persistence-jsonl` 이 파일로 저장
2. `dsh-session-title-first-prompt-llm` 이 첫 문장으로 대화 제목 생성
3. `dsh-system-prompt` 와 `dsh-agent-instructions` 가 시스템 프롬프트 조립
4. `dsh-tools` 가 켜져 있는 도구 목록을 모델에게 넘길 형태로 구성

**모델 호출**

5. `dsh-llm-pi-ai` 가 요청 전송. 실패하면 `dsh-llm-retry` 가 재시도

**도구 실행**

6. 모델이 도구를 고르면 해당 도구 플러그인이 실행
7. `dsh-sandbox-policy` 가 허용 범위를 판단하고, 걸리면 `dsh-user-approval` 이 승인을 요청

**반복**

8. `dsh-agent-loop` 가 결과를 다시 모델에 넣고 5번으로 회귀
9. `dsh-token-meter` 가 토큰을 계량

**컨텍스트가 찰 때**

10. `dsh-compaction-tool-result-pruner` 가 기준 길이를 넘는 도구 결과부터 잘라냄
11. 그래도 모자라면 `dsh-compaction-basic` 이 대화를 압축

모델이 개입하는 구간은 6번뿐이다. 나머지는 런타임이 조건에 따라 자동으로 돌린다.

## 등록형과 동작형

플러그인은 두 갈래로 나뉜다.

| 갈래 | 하는 일 | 예 |
| --- | --- | --- |
| 등록형 | 모델이 쓸 것을 붙여 준다 | `dsh-tool-bash`, `dsh-skill`, `dsh-mcp-client` |
| 동작형 | 등록하는 것 없이 흐름 자체를 맡는다 | `dsh-agent-loop`, `dsh-compaction`, `dsh-user-approval`, `dsh-system-prompt` |

동작형이 할 수 있는 일은 세 가지다.

- 도구 호출을 관찰한다 (기록, 계량)
- 흐름에 끼어든다 (승인 요청, 차단)
- 모델에게 가는 내용을 고친다 (압축, 프롬프트 조립)

MCP로는 이 셋 중 어느 것도 할 수 없다. MCP 서버는 호출당하는 쪽이므로 다른 도구가
언제 불렸는지 알 수 없고 흐름에 개입할 수도 없다.

## 도구, 스킬, MCP와의 관계

도구와 스킬과 MCP는 모두 플러그인이 등록한 결과물이다. 플러그인이 한 층 위에 있다.

```
플러그인
├── dsh-tool-bash      모델에게 bash 도구를 등록
├── dsh-skill          모델에게 스킬을 등록
├── dsh-mcp-client     MCP 서버의 도구를 등록
├── dsh-agent-loop     등록하지 않는다. 모델을 반복 호출하는 쪽
├── dsh-compaction     등록하지 않는다. 대화 압축
└── dsh-system-prompt  등록하지 않는다. 프롬프트 조립
```

## 다른 도구와의 차이

에이전트 분야에서 플러그인이라는 말은 대개 도구를 추가하는 것을 뜻한다. 곧 등록형이다.
dsh가 쓰는 뜻은 런타임을 이루는 구성 단위이며, 이는 에이전트 분야가 아니라 Cordis라는
범용 프레임워크에서 온 개념이다.

동작형까지 교체할 수 있다는 점이 차이의 핵심이다. 압축 전략, 재시도 방식, 시스템
프롬프트, 승인 정책은 에이전트 성능이 갈리는 지점인데 다른 제품은 이를 고정해 둔다.
