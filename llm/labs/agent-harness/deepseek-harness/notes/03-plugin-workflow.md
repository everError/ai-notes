# 플러그인을 다루는 세 가지 층위

"모든 것이 플러그인"이 실제로 무엇을 뜻하는지 정리한다. 손대는 방법이 세 층으로
나뉘며, 아래로 갈수록 개입 정도가 크다.

## 층위 1 — 프로필 패치로 구성 바꾸기

가장 흔한 방법이다. 프로필의 플러그인 목록을 사용자 패치로 덮어쓴다.

대상 파일은 `$DSH_HOME/profiles/<프로필>/cordis.patch.yml` 이다. 트리는 다음 순서로
합성되며, 뒤에 오는 계층이 앞을 이긴다.

1. `package.json` 의 `dsh.profile.bundles` 에 적힌 번들들의 패치
2. 프로필의 `cordis.patch.yml`
3. `--patch` 로 넘긴 덮어쓰기 파일

패치 항목은 행의 `id` 를 대상으로 삼는다. 같은 id 에 대해 마지막에 쓴 값이 이기며,
`config` 는 병합이 아니라 통째로 교체된다.

행 하나는 다음 형태다.

```yaml
- id: tool-fs-search
  name: '@deepseek-ai/dsh-tool-fs-search'
  config:
    sampleOverCapGlobResults: false
```

이미 있는 행을 고칠 때는 최상위에 `id` 를 적어 덮어쓴다. `insert` 는 새 행을 넣는
조작이므로, 이미 존재하는 id 를 `insert` 로 넣으면 부팅이 `duplicate loader entry id`
오류로 실패한다. 어떤 id 가 이미 있는지는 번들의 `cordis.patch.yml` 을 확인한다.

`disabled` 로 끌 수 있고, 값에 `!!js` 표현식을 쓸 수 있다. 기본 프로필도 이 방식으로
운영 체제를 가른다.

```yaml
- id: tool-bash
  name: '@deepseek-ai/dsh-tool-bash'
  disabled: !!js process.platform === 'win32'
```

행 순서는 적재 순서를 뜻하지 않는다. 활성화는 필요한 서비스가 갖춰졌는지에 따라
결정되므로, 순서는 읽는 사람을 위한 묶음일 뿐이다.

## 층위 2 — 에이전트 프리셋 고르기

에이전트 프리셋은 한 세션이 쓸 구성 묶음이다. 기본 설치본에 네 가지가 들어 있다.

| 프리셋 | 내용 |
| --- | --- |
| `minimal` | 최소 구성 |
| `standard` | 기본값 |
| `code` | 코딩 작업용 |
| `cordis` | `standard` 에 자기 참조 도구와 구성 작성 스킬을 더한 것 |

화면의 프리셋 선택기에서 고른다. 프로필 패치를 고칠 필요가 없다.

`cordis` 프리셋을 고르면 모델에게 도구 다섯 개가 붙는다.

| 도구 | 하는 일 |
| --- | --- |
| `cordis_inspect` | 살아 있는 런타임 조회. 서비스, 플러그인, 등록된 도구, 사용 가능한 api 와 이벤트 |
| `cordis_define` | 플러그인 정의 기록. 문법 검사만 하고 실행하지는 않는다 |
| `cordis_run` | 호스트 절반을 샌드박스에서 평가하고 브라우저 절반을 화면에 전달 |
| `cordis_stop` | 실행 중지. 정의는 남는다 |
| `cordis_undefine` | 정의까지 삭제 |

프로필 패치로 `tool-cordis` 행을 직접 넣으면 안 된다. 프리셋이 같은 도구를 올리므로
`Host Cordis inspect provider "Service" is already registered` 오류로 세션이 열리지 않는다.

프리셋은 호스트 구성과 층이 다르다. 호스트 구성은 세션 전체가 공유하는 것을 담고
(저장, 샌드박스, 승인, 모델 경로, 서브에이전트 등록소), 프리셋은 한 세션이 거기에
얹는 것을 담는다(도구, 페르소나, 프롬프트 구획). 서비스를 발행하는 행은 호스트
구성에 속한다.

직접 만든 프리셋은 `$DSH_HOME/.agent-presets/<id>/` 에 프리셋마다 디렉터리 하나로 둔다.
설치본에 딸려 온 프리셋은 고치지 않는다. 판올림 때 덮어써지며, `cordis` 프리셋을
망가뜨리면 이 기능 자체를 못 쓰게 된다. 바꾸려면 복사해서 새 프리셋으로 만든다.

제약도 분명하다. 이렇게 올린 플러그인은 프로세스 메모리에만 존재한다. 파일을 만들지
않고 설정도 바꾸지 않으며, 재시작하면 사라진다. 세션 단위로 격리되어 정의한 세션에서만
보인다. 문서는 이 프리셋의 세션을 셸 접근과 같은 수준으로 취급하라고 적고 있다.

## 층위 3 — 정식 플러그인 만들기

플러그인은 npm 패키지다. 패키지의 `package.json` 에 `dsh.bundle.patch` 로 자기 패치
파일을 가리키고, 프로필에서 그 패키지를 번들로 참조하거나 패치로 행을 추가한다.
이 방식만 재시작 후에도 남는다.

## 정리

| 목적 | 층위 |
| --- | --- |
| 도구를 끄거나 설정값을 바꾼다 | 1 |
| 런타임 구조를 살펴보거나 일회성 확장을 시험한다 | 2 |
| 계속 쓸 기능을 만든다 | 3 |
