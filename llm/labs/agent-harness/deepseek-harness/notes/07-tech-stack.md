# dsh에 쓰인 기술

설치본의 의존성 229개를 훑어 계층별로 정리했다. 무엇을 왜 골랐는지가 설계 판단을
그대로 보여준다.

## 기반

| 기술 | 역할 | 비고 |
| --- | --- | --- |
| TypeScript | 전 계층 | 타입 선언까지 배포한다 |
| ESM | 모듈 체계 | 모든 패키지가 `"type": "module"` |
| Node.js | 실행 환경 | 최근 판을 요구한다 |
| pnpm 작업 공간 | 저장소 구성 | 패키지 200여 개를 하나의 저장소로 관리 |
| Cordis | 플러그인 커널 | 외부 프레임워크를 `vendor/` 에 담아 쓴다 |

## 모델 접근

| 기술 | 역할 |
| --- | --- |
| `@earendil-works/pi-ai` | 통합 LLM API. 모델 탐색과 프로바이더 설정을 담당 |
| `@anthropic-ai/sdk` | Anthropic 접근 |
| `@google/genai` | Google 접근 |
| `@mistralai/mistralai` | Mistral 접근 |
| `@aws-sdk/*` | Bedrock 접근 |

주목할 점은 프로바이더 SDK를 직접 부르지 않고 `pi-ai` 라는 외부 통합 계층을 한 겹
두었다는 것이다. `dsh-llm-pi-ai` 플러그인이 그 계층을 감싼다. 자체 추상화를 만드는
대신 남의 것을 쓰는 판단이며, 그만큼 프로바이더 확장이 dsh 코드와 분리된다.

## 도구와 스키마

| 기술 | 역할 |
| --- | --- |
| `@modelcontextprotocol/sdk` | MCP 서버 연결 |
| `zod` + `zod-to-json-schema` | 도구 스키마 정의와 모델용 JSON Schema 변환 |
| `schemastery` | 플러그인 설정 스키마. 설정 화면을 자동으로 만든다 |
| `ajv` | JSON Schema 검증 |

도구 인자 스키마와 플러그인 설정 스키마에 서로 다른 도구를 쓴다. 앞은 모델에게
넘길 JSON Schema 가 필요하고, 뒤는 설정 화면을 자동 생성해야 하기 때문이다.

60여 개로 쪼개 Cordis 로 합성한다.

## 실행과 격리

| 기술 | 역할 |
| --- | --- |
| `node:vm` | 모델이 쓴 코드의 격리 실행 |
| Landlock | 리눅스에서 하위 프로세스 제한. 미리 빌드된 정적 실행 파일을 함께 배포 |
| Windows ACL | 윈도우에서 같은 목적 |
| `node-pty` | 실제 터미널 프로세스. 지속 셸 세션에 쓴다 |
| `cross-spawn` | 플랫폼 차이를 흡수한 프로세스 실행 |

격리 수단을 운영 체제마다 따로 마련했다. 다만 `node:vm` 은 전역만 가릴 뿐이라
문서가 보안 경계가 아니라고 명시한다.

## 저장과 관측

| 기술 | 역할 |
| --- | --- |
| `node:sqlite` | 세션 조회. Node 내장 모듈을 쓴다 |
| JSONL | 세션 기록 저장 |
| OpenTelemetry | 추적, 지표, 로그 내보내기 |
| `chokidar` | 파일 변경 감시. 플러그인 다시 적재에 쓴다 |

SQLite 를 외부 패키지가 아니라 Node 내장 모듈로 붙인 것이 눈에 띈다. 네이티브
빌드 단계가 사라지므로 설치가 단순해진다. 대신 요구 Node 판이 올라간다.

## 읽어낼 수 있는 판단

- **직접 만들지 않는다.** 모델 통합(`pi-ai`), 플러그인 커널(Cordis), 코드 강조(shiki)를 전부 기존 것으로 해결했다. 자체 구현한 것은 하네스 고유 영역뿐이다
- **내장 기능을 우선한다.** SQLite 와 격리 실행을 Node 내장으로 처리해 네이티브 의존을 줄였다
- **플랫폼 차이를 정면으로 다룬다.** 격리 수단을 운영 체제마다 준비하고, 도구 자체도 플랫폼에 따라 갈라 적재한다
- **스키마를 두 종류로 나눈다.** 모델에게 줄 것과 사람에게 줄 것의 요구가 다르다고 보았다
