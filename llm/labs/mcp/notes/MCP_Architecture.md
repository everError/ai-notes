# MCP 아키텍처 — 에이전트·클라이언트·서버·툴의 관계

이 문서는 특정 SDK나 프레임워크에 종속되지 않은 일반적인 **Model Context Protocol (MCP)** 구조에서 AI 에이전트, MCP 클라이언트, MCP 서버, 서버 내 Tool 이 어떤 역할을 맡고 어떻게 맞물리는지 정리한 것입니다.

> **기준 스펙: 2026-07-28**
> 이 버전에서 프로토콜 코어가 stateless 로 전환되었습니다. 세션과 핸드셰이크를 전제로 한 이전 설명(`initialize` 교환, `Mcp-Session-Id` 유지, 서버가 열린 스트림으로 클라이언트에 되묻는 방식)은 더 이상 유효하지 않습니다. 기존 구현을 옮기는 절차는 [MCP_Stateless_Migration](MCP_Stateless_Migration.md) 을 참고합니다.

---

## 1. 주요 구성 요소

### 호스트 / 에이전트

- LLM 을 활용하여 사용자 입력을 분석하고, 필요한 경우 외부 도구를 호출할지 판단하는 의사결정 주체
- 어떤 서버에 연결할지, 어떤 도구 호출을 사용자에게 승인받을지 결정하는 신뢰 경계
- 예: LangGraph 에이전트, Semantic Kernel, Claude Desktop, 커스텀 Python/C#/Rust 에이전트

### MCP 클라이언트

- 호스트 안에서 동작하며, 하나의 MCP 서버와 연결을 담당하는 계층
- 요청을 직렬화하여 전송하고 응답을 해석
- stateless 전환 이후 역할이 하나 늘었습니다. **매 요청마다 프로토콜 버전과 클라이언트 정보를 스스로 실어 보내야 하고**, 서버가 추가 입력을 요구하면 재호출 루프를 돌려야 합니다
- 로컬 서버를 서브프로세스로 실행·관리하는 것은 stdio 전송에 한정된 이야기이며, 원격 HTTP 서버에는 해당하지 않습니다

### MCP 서버

- 요청을 받아 적절한 기능을 실행하고 결과를 반환
- **인스턴스가 상태를 들고 있지 않습니다.** 어떤 요청이든 어느 인스턴스로 가도 처리 가능해야 하며, 여러 왕복이 필요한 작업의 중간 상태는 `requestState` 로 클라이언트에 되돌려 보관합니다
- 예: FastMCP 기반 서버, rmcp 기반 서버, Node.js MCP 서버

### 서버가 노출하는 것

| 종류         | 설명                                    | 제어 주체     |
| ------------ | --------------------------------------- | ------------- |
| **Tool**     | 실행 가능한 기능. 부수효과를 가질 수 있음 | 모델          |
| **Resource** | 읽기 전용 데이터·컨텍스트                | 애플리케이션  |
| **Prompt**   | 재사용 가능한 프롬프트 템플릿            | 사용자        |

## 2. Stateless 코어

2026-07-28 스펙의 가장 큰 변화입니다. 프로토콜에서 세션 개념이 사라졌습니다.

**제거된 것**

- `initialize` / `initialized` 핸드셰이크
- `Mcp-Session-Id` 헤더와 그에 묶인 세션 수명주기

**대체 방식** — 모든 요청이 자기 자신을 설명합니다.

- HTTP 헤더 `MCP-Protocol-Version: 2026-07-28`
- `params._meta` 안에 클라이언트 정보와 역량

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "otters" },
    "_meta": {
      "io.modelcontextprotocol/clientInfo": { "name": "my-app", "version": "1.0" }
    }
  }
}
```

**운영상 의미**

세션을 공유 저장소에 보관하거나 sticky session 을 설정할 필요가 없어졌습니다. 서버 인스턴스를 일반적인 라운드로빈 로드밸런서 뒤에 그냥 여러 개 띄우면 되고, 인스턴스가 재시작되어도 진행 중이던 대화가 끊기지 않습니다. MCP 서버가 특수한 배포 대상에서 **평범한 HTTP 서비스**로 내려온 것이 이 변경의 핵심입니다.

---

## 3. 전송 계층

| 전송                | 용도                          | 상태                          |
| ------------------- | ----------------------------- | ----------------------------- |
| **stdio**           | 로컬 서브프로세스로 실행      | 유효. 로컬 도구의 기본 선택   |
| **Streamable HTTP** | 원격 서버                     | 권장                          |
| HTTP + SSE (legacy) | 구 원격 전송                  | 폐기. 최소 12개월 유예        |

WebSocket 은 MCP 공식 전송이었던 적이 없습니다. 개별 구현체가 자체적으로 얹은 경우는 있으나 스펙 범위 밖입니다.

---

## 4. 라우팅 — 두 층위로 분리되었습니다

이 구분이 이전 문서에서 가장 부정확했던 부분입니다. 라우팅은 인프라 층위와 서버 내부 층위로 나뉩니다.

### 인프라 층위 — 헤더 기반

요청은 다음 두 헤더를 포함해야 합니다.

- `Mcp-Method` — 호출하는 메서드 (`tools/call`, `resources/read` 등)
- `Mcp-Name` — 대상 이름 (도구명 등)

게이트웨이·리버스 프록시·레이트리미터가 **JSON 본문을 파싱하지 않고** 헤더만으로 라우팅하고 인가하고 제한을 걸 수 있습니다. 도구 단위로 요청량을 제한하거나, 특정 도구만 별도 백엔드로 보내는 구성이 표준 HTTP 인프라만으로 가능해집니다.

### 서버 내부 층위 — 이름 기반 디스패치

서버는 `params.name` 으로 실제 핸들러를 찾아 실행합니다. 이 부분은 이전과 동일합니다.

## 5. Multi Round-Trip Requests (MRTR)

stateless 코어에서는 서버가 열린 스트림으로 클라이언트에 되물을 수 없습니다. 그래서 "실행 도중 사용자 확인이 필요한" 작업을 표현하는 방식이 바뀌었습니다.

**1단계 — 서버가 추가 입력을 요구**

```json
{
  "resultType": "input_required",
  "inputRequests": {
    "confirm": {
      "type": "elicitation",
      "message": "Delete 3 files?",
      "schema": { "type": "boolean" }
    }
  },
  "requestState": "eyJzdGVwIjoxLCJmaWxlcyI6WyJhIiwiYiIsImMiXX0="
}
```

**2단계 — 클라이언트가 답을 채워 재호출**

클라이언트는 사용자에게 확인을 받은 뒤, `inputResponses` 에 답을 담고 `requestState` 를 **그대로 되돌려** 같은 메서드를 다시 호출합니다.

`requestState` 는 서버가 자기 메모리에 두던 중간 상태를 불투명한 값으로 만들어 클라이언트에 맡긴 것입니다. 덕분에 재호출이 처음과 다른 인스턴스에 도착해도 이어서 처리할 수 있습니다. 서버 구현 관점에서는 **중간 상태를 직렬화 가능한 형태로 설계해야 한다**는 제약이 새로 생긴 셈입니다.

---

## 6. 목록 결과 캐싱

`tools/list`, `prompts/list`, `resources/list` 응답에 캐싱 정보가 붙습니다.

- `ttlMs` — 유효 기간
- `cacheScope` — 사용자 간 공유가 안전한 캐시인지 여부

재연결 때마다 전체 목록을 다시 받던 낭비가 줄고, 상위 캐시 계층이 안정적으로 동작합니다. 서버 구현 시 목록이 사용자별로 달라지면 `cacheScope` 를 반드시 좁게 잡아야 합니다. 이 값을 잘못 설정하면 다른 사용자에게 노출되면 안 되는 도구 목록이 공유될 수 있습니다.

## 7. 실행 흐름

```text
사용자 입력
   ↓
[에이전트 (LLM)]  도구 호출 필요 판단
   ↓
[MCP 클라이언트]  요청 생성
                  · MCP-Protocol-Version 헤더
                  · Mcp-Method / Mcp-Name 헤더
                  · params._meta 에 clientInfo
   ↓
[게이트웨이]      헤더만 보고 라우팅 · 인가 · 레이트리밋
   ↓
[MCP 서버 인스턴스 N]  (어느 인스턴스든 무방)
   ↓
[Tool 실행]
   ↓
   ├─ 완료  → 결과 반환
   └─ 추가 입력 필요 → resultType: "input_required" + requestState
                        ↓
                    [클라이언트가 사용자 확인]
                        ↓
                    inputResponses + requestState 로 재호출 (5절)
   ↓
[에이전트가 결과 해석 → 최종 답변 생성]
```

## 8. 구성 요소 간 관계 요약

| 구성 요소     | 호출 대상     | 역할 요약                                                    |
| ------------- | ------------- | ------------------------------------------------------------ |
| 에이전트      | MCP 클라이언트 | 도구 호출 필요 여부 판단, 사용자 승인 획득                   |
| MCP 클라이언트 | MCP 서버      | 요청 자기기술(버전·clientInfo), 전송, MRTR 재호출 루프 수행   |
| 게이트웨이    | MCP 서버      | `Mcp-Method`/`Mcp-Name` 헤더 기반 라우팅·인가·레이트리밋      |
| MCP 서버      | Tool          | `params.name` 으로 디스패치, 중간 상태를 `requestState` 로 외부화 |
| Tool          | 내부 로직     | 실제 응답 생성, 외부 API 호출, 계산 등 수행                  |

## 9. 생애주기 정책과 폐기 목록

모든 기능에 **Active → Deprecated → Removed** 단계가 정의되었고, 폐기 선언부터 제거 가능 시점까지 최소 12개월이 보장됩니다. 이전처럼 스펙 개정마다 즉시 깨지는 상황은 없어집니다.

| 기능                | 상태          | 비고                                            |
| ------------------- | ------------- | ----------------------------------------------- |
| Roots               | 폐기          | 최소 12개월 동작 유지                           |
| Sampling            | 폐기          | 최소 12개월 동작 유지                           |
| Logging             | 폐기          | 최소 12개월 동작 유지                           |
| Tasks               | 코어에서 이동 | `io.modelcontextprotocol/tasks` 확장으로 이관   |
| `tasks/list`        | 제거          | 세션이 없어 범위를 정의할 수 없음               |
| HTTP + SSE 전송     | 폐기          | Streamable HTTP 로 대체                         |
| Dynamic Client Registration | 폐기  | CIMD 로 대체, 하위 호환용으로만 유지            |

Tasks 는 폴링 방식 `tasks/get` 과 새로 추가된 `tasks/update` 로 동작합니다.

## 10. 인가

- **RFC 9207 issuer 검증** — 인가 서버 혼동(mix-up) 공격 차단. 자격증명이 특정 인가 서버에 바인딩됩니다
- **`application_type`** — CLI·데스크톱 앱의 localhost 리다이렉트 문제 해소
- **CIMD (Client ID Metadata Documents)** — 권장 클라이언트 등록 방식. 인가 서버마다 등록해서 불투명한 `client_id` 를 발급받는 대신, 클라이언트가 고정된 HTTPS URL 에 메타데이터 문서를 게시하고 **그 URL 자체가 `client_id` 가 됩니다**

## 11. 확장 프레임워크

새 기능은 이제 코어에 바로 들어가지 않고 **선택적 확장**으로 먼저 출시되어 안정화 기간을 거칩니다. 코어로 승격되지 않고 확장으로 남을 수도 있습니다.

확장은 역-DNS 형태의 이름을 씁니다(예: `io.modelcontextprotocol/tasks`). MCP Apps 처럼 별도 스펙으로 논의되던 기능들도 이 체계 위에 놓입니다.

---

## 12. 핵심 요약

- MCP 는 에이전트가 외부 도구를 호출하도록 표준화한 메시지 기반 프로토콜이다. 이 전제 자체는 변하지 않았다.
- **프로토콜 코어가 stateless 다.** 세션과 핸드셰이크가 없고, 모든 요청이 버전·클라이언트 정보를 스스로 싣는다.
- **라우팅이 헤더로 올라왔다.** 게이트웨이가 본문을 열지 않고 도구 단위로 제어할 수 있다.
- **서버가 되묻는 방식이 MRTR 로 바뀌었다.** 중간 상태는 `requestState` 로 클라이언트가 보관한다.
- **폐기에 12개월 유예가 생겼다.** 급하게 대응할 필요는 없으나, Roots·Sampling·Logging 에 의존하는 구현은 대체 경로를 계획해야 한다.
- 결과적으로 MCP 서버 운영이 특수 작업에서 **일반적인 무상태 HTTP 서비스 운영**으로 수렴한다.
