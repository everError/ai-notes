# 에이전트 루프를 스트리밍으로 내보내기

마지막 응답만 스트리밍되고, 추론과 답변이 여러 차례 오가는 과정은 매끄럽게
전달되지 않는 문제를 정리한다.

## 증상

에이전트가 도구를 부르고 다시 생각하고 또 부르는 동안 화면이 멈춘 것처럼 보인다.
모든 것이 끝난 뒤에야 마지막 답변이 흘러나온다. 단발 대화는 잘 되는데 여러 단계
작업에서 무너진다.

## 원인 1 — 전송 단위를 모델 호출에 묶었다

가장 흔한 구조적 원인이다. 요청 하나에 모델 호출 하나를 대응시키고 그 응답을
스트리밍하면, 루프가 한 바퀴 돌 때마다 전송이 끝난다. 두 번째 호출부터는 실어
보낼 통로가 없다.

전송 단위를 **한 번의 실행 전체**로 잡아야 한다. 통로를 먼저 열고 그 위로 여러
종류의 이벤트를 계속 흘려보낸다.

```
잘못된 구조   요청 → 모델 호출 → 스트림 → 종료 → (루프는 계속 도는데 통로가 없음)
맞는 구조     요청 → 통로 개설 → [모델 호출, 도구 실행, 모델 호출 ...] → 종료
```

## 원인 2 — 프레임워크 기본값이 최종 결과만 준다

그래프나 체인을 쓰는 경우 기본 스트림이 단계별 결과만 내보내는 경우가 많다.
글자 단위 흐름과 중간 상태를 함께 받으려면 스트림 방식을 따로 지정해야 한다.
프레임워크마다 이름은 다르나 대체로 다음이 갈린다.

| 받고 싶은 것 | 지정해야 하는 것 |
| --- | --- |
| 글자 단위 흐름 | 메시지 조각 방식 |
| 노드별 상태 변화 | 상태 갱신 방식 |
| 직접 만든 진행 표시 | 사용자 정의 이벤트 방식 |

여러 방식을 함께 켜서 하나의 통로로 합치는 것이 보통이다.

## 원인 3 — 도구 구간에는 보낼 글자가 없다

이것이 가장 흔한 착시다. 모델이 도구를 부르기로 결정한 순간 사용자에게 보여줄
문장은 나오지 않는다. 도구가 실행되는 동안도 마찬가지다. 그래서 그 구간이
비어 보인다.

잘 만든 제품이 매끄러워 보이는 이유는 그 구간을 **다른 종류의 이벤트로 채우기**
때문이다.

- 어떤 도구를 어떤 인자로 부르는지
- 도구가 무엇을 돌려주었는지
- 지금 몇 번째 단계인지, 할 일 목록의 어디쯤인지

글자 흐름만 화면에 연결해 두면 이 구간이 공백이 된다. 도구 호출과 결과도 이벤트로
받아 표시해야 한다.

## 원인 4 — 전송 규격에 여러 메시지를 담을 수 없다

앞의 원인들보다 근본적인 지점이다. 채팅 완료 규격을 그대로 쓰는 경우가 많은데,
그 규격은 **응답 하나에 조수 메시지 하나**를 전제한다.

- 본문을 실어 나르는 통로가 하나뿐이다
- 종료 표시가 한 번만 나오고 그것으로 끝난다
- 도구 호출 항목은 "받는 쪽이 실행하라"는 뜻이지 "지금 이런 일을 하고 있다"는 표시가 아니다
- 화면 조각을 실을 자리가 없다

이 규격 위에서 "응답 → 진행 → 응답"을 만들려 하면 표현할 자리가 없다. 결국
모든 것을 마지막 메시지 하나에 몰아넣게 된다.

### 우회로와 그 대가

규격을 유지한 채 밀어붙이면 대체로 두 가지를 하게 된다.

**비표준 항목 추가.** 조각에 규격에 없는 키를 넣어 추론 내용이나 화면 정보를 함께
보낸다. 동작은 하지만 그 규격을 기대하는 클라이언트와 호환이 깨진다.

**본문에 표시를 심어 보내기.** 화면 정보를 본문 텍스트 안에 특정 표시로 감싸
보내고 받는 쪽이 걸러 낸다. 이것이 특히 비싸다.

- 모델이 그 표시를 정확히 만들어 내야 한다. 못 하면 그대로 본문에 노출된다
- 조각 단위로 오므로 표시가 중간에서 잘린다. 글자 단위 상태 기계가 필요하다
- 표시의 첫 글자가 본문에 우연히 나오면 판별될 때까지 출력을 멈춰야 한다
- 표시가 아니었음이 밝혀지면 멈춰 둔 것을 되돌려 내보내야 한다

통로가 하나뿐이라 본문 안에 신호를 섞는 것이고, 그 복잡도는 전부 규격의 한계에서
온다. 채널을 나누면 사라지는 문제다.

### 어떻게 바꾸는가

| 방향 | 내용 |
| --- | --- |
| 규격을 바꾼다 | 종류가 나뉜 이벤트 스트림으로 옮긴다. 메시지 시작과 끝, 도구 호출, 상태 변화, 화면 정보가 각각 자기 자리를 갖는다 |
| 채널만 나눈다 | 규격은 두되 본문 표시 대신 별도 이벤트로 화면 정보를 내보낸다. 그래프 프레임워크의 사용자 정의 이벤트 통로를 쓴다 |
| 중간 말을 기대하지 않는다 | 진행 상황을 문장이 아니라 구조화된 상태로 표현하고, 그 변화를 화면이 그린다 |

세 번째가 실무에서 가장 안정적이다. 모델에게 "도구를 부르기 전에 한마디 하라"고
시키는 것은 모델에 따라 지켜지기도 하고 안 지켜지기도 한다. 할 일 목록 같은 상태를
두고 그 변화를 표시하면 모델이 말을 하지 않아도 화면이 움직인다.

## 원인 5 — 메시지 경계를 관리하지 않았다

한 번의 실행에서 모델이 여러 번 말한다. 클라이언트가 이것을 구분하지 못하면 둘 중
하나가 된다. 말풍선이 계속 새로 생기거나, 앞의 내용을 덮어쓴다.

각 조각에 실행 식별자와 메시지 식별자를 실어 보내고, 클라이언트가 그것으로 묶어야
한다. 시작과 끝을 알리는 이벤트가 함께 있으면 더 안정적이다.

```
run_start
  message_start(id=1) → delta → delta → message_end(id=1)
  tool_call(id=a) → tool_result(id=a)
  message_start(id=2) → delta → ... → message_end(id=2)
run_end
```

## 원인 6 — 중간에서 버퍼링된다

코드는 맞는데 뭉쳐서 오는 경우다. 확인할 곳이 정해져 있다.

| 지점 | 확인 |
| --- | --- |
| 역방향 프록시 | 응답 버퍼링을 끈다 |
| 압축 | 스트림 경로에서 압축을 끄거나 조각마다 내보낸다 |
| 서버 프레임워크 | 조각을 쓴 뒤 즉시 내보내는지 |
| 클라이언트 | 응답 전체를 기다리는 방식으로 읽고 있지 않은지 |

전부 정상인데 뭉친다면 조각 하나가 너무 작아 네트워크 계층에서 모이는 경우도 있다.

## 원인 7 — 추론 내용은 다른 채널로 온다

추론을 따로 내보내는 모델은 그것을 본문과 다른 자리에 담는다. 본문만 화면에
연결해 두면 모델이 오래 생각하는 동안 아무것도 보이지 않는다. 추론 조각을 별도
이벤트로 받아 접이식 영역 등으로 표시하면 그 구간이 채워진다.

## 끊겼을 때

긴 작업일수록 중간에 연결이 끊긴다. 이어받으려면 각 이벤트에 순번을 붙이고,
클라이언트가 마지막으로 받은 순번을 알려 그 다음부터 다시 받는 구조가 필요하다.
서버는 최근 이벤트를 잠시 보관해야 한다.

여기까지 하지 않으면 새로 고침 한 번에 진행 중인 작업을 놓친다.

## 점검 목록

| 항목 | 확인 |
| --- | --- |
| 통로가 실행 전체를 덮는가 | 모델 호출마다 끊기지 않는지 |
| 규격이 여러 메시지를 담을 수 있는가 | 본문에 표시를 심어 우회하고 있지 않은지 |
| 도구 호출과 결과를 이벤트로 보내는가 | 빈 구간이 채워지는지 |
| 상태 변화를 부분만 보내는가 | 전체를 다시 보내고 있지 않은지 |
| 메시지 경계를 식별자로 구분하는가 | 말풍선이 어긋나지 않는지 |
| 버퍼링이 꺼져 있는가 | 뭉쳐 오지 않는지 |
| 추론 채널을 따로 받는가 | 생각하는 동안 공백이 아닌지 |
| 재연결로 이어받는가 | 새로 고침에 작업을 놓치지 않는지 |

이 목록이 곧 전송 규격이 표준화하려는 항목들이다. 직접 만들면 하나씩 부딪히게
되므로, 규격을 먼저 읽고 무엇이 필요한지 확인하는 편이 빠르다.
