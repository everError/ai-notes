# Decision Model (결정 모델) 정리

## 한 줄 요약

- **Decision Model**: 글을 생성하지 않고, 정해진 질문과 선택지에 대해 **타입이 있는 답과 확률**을 반환하는 모델
- **LLM**: 자유 텍스트를 생성하는 모델

둘 다 텍스트를 입력받지만 **출력**이 다릅니다. 결정 모델은 LLM이 하던 "프롬프트 작성 → 생성 → 파싱" 과정을 한 번의 타입 있는 호출로 대체합니다.

> 2026년 9월에 등장한 새로운 범주입니다. 아래 수치 중 상당수는 벤더 발표이거나 비교 글의 측정치이며, 독립 검증은 충분하지 않습니다.

---

## 왜 필요한가

단일 판단(티켓 분류, 스팸 여부, 다음 행동 선택)에도 LLM을 호출하면 세 가지 비용이 발생합니다.

| 항목        | 설명                                                    |
| ----------- | ------------------------------------------------------- |
| 지연        | 생성 모델 호출에 보통 0.5~2초가 걸림                    |
| 비용        | 한 비트짜리 판단에 생성 토큰 비용을 지불                |
| 파싱 불안정 | 출력 문자열에서 라벨을 추출해야 하며, 형식이 어긋나면 재시도 필요 |

결정 모델은 답 공간을 처음부터 제한해서 이 세 가지를 줄입니다.

---

## System One / System Two

카너먼의 『생각에 관한 생각』에서 따온 비유입니다.

| 구분             | 역할                         | 해당 모델                    |
| ---------------- | ---------------------------- | ---------------------------- |
| **System One**   | 빠르고 직관적인 패턴 판단    | 결정 모델 (Jev, Laya 등)     |
| **System Two**   | 느리고 숙고하는 추론         | 채팅 LLM, 추론 모델          |

TypeSafe가 결정 모델 범주를 "System One 모델"이라고 부릅니다. 실무에서는 두 가지를 조합합니다.

```
계획·추론·작성  → 강한 LLM (System Two)
분기·필터·게이트 → 결정 모델 (System One)
```

---

## 동작 방식

```
상태(텍스트/JSON/이미지) + 질문(유한한 선택지)
        ↓
   결정 모델 (설명·추론 과정 없음)
        ↓
타입 있는 답 + 확률 (+ 신뢰도)
        ↓
   애플리케이션 코드가 분기
        ↓
   정책 계층이 권한·범위를 별도로 검증
```

핵심 원칙은 **모델은 추천만 하고, 허용 여부는 코드가 결정한다**는 것입니다. 권한, 범위, 호출 빈도 제한은 모델 밖의 정책 계층에서 처리합니다.

---

## 구현 방식 두 가지

| 방식                | 설명                                                       | 예시                  |
| ------------------- | ---------------------------------------------------------- | --------------------- |
| **제약된 LLM**      | 기존 LLM의 답 공간을 선택지로 제한하는 인터페이스를 얹음   | OpenAI Decisions API  |
| **목적 특화 모델**  | 처음부터 결정용으로 학습하며 텍스트 생성 기능이 없음       | Jev, Laya             |

- **Jev**: 보정된 확률을 얻도록 강화학습(Reinforcement Learning for Calibrated Decisions)으로 학습했다고 소개됩니다.
- **Laya**: 양방향 인코더(비자기회귀)로 입력 전체를 한 번에 읽고, 각 선택지에 점수를 매깁니다. 토큰을 순서대로 생성하지 않습니다.

---

## 대표 모델

| 구분       | **Jev** (TypeSafe)             | **Decisions API** (OpenAI)        | **Laya**              |
| ---------- | ------------------------------ | --------------------------------- | --------------------- |
| 방식       | 목적 특화                      | GPT-6 Luna 제약                   | 목적 특화 (인코더)    |
| 모델 ID    | `typesafe/jev-1.13`            | `gpt-6-luna` 기반                 | 오픈소스              |
| 출시       | 2026-09-15, 즉시 사용 가능     | 2026-09-29, 제한적 프리뷰         | 오픈소스, 다국어      |
| 입력       | 텍스트                         | 텍스트 + 이미지                   | 텍스트                |
| 가격       | 입력 $0.042/M, 출력 무료       | 미공개                            | 오픈소스              |
| 지연       | 실측 P50 0.21초, P95 0.34초    | 발표 기준 150ms                   | 발표 기준 약 33ms     |
| 컨텍스트   | 32K (OpenRouter 기준)          | 미공개                            | 확인하지 못함         |
| 확률 제공  | 선택지별 확률 + 신뢰도         | 미확인                            | 선택지별 점수         |

- Jev와 Decisions API는 정확도가 비슷하다는 평가가 많습니다. 이미지가 필요하면 OpenAI가, 가격 공개·확률 제공·즉시 사용 가능성은 Jev가 유리합니다.
- Decisions API는 요청·응답 스키마와 가격이 공개되기 전이어서 세부 사항은 변경될 수 있습니다.

## Jev의 질문 유형 (3가지)

| 유형       | 설명                                           | 반환값                                 |
| ---------- | ---------------------------------------------- | -------------------------------------- |
| **Choice** | 선택지 중 하나를 선택                          | 선택 결과, 선택지별 확률, 신뢰도(0~1)  |
| **Score**  | 직접 정의한 순서형 기준으로 평가               | 확률 가중 점수, 수준별 확률, 신뢰도    |
| **Noul**   | 참/거짓 명제가 참일 확률                       | 확률(0~1)                              |

한 번의 호출에 여러 질문을 섞을 수 있습니다.

**요청 예시:**

```json
POST https://openrouter.ai/api/alpha/decisions

{
  "model": "typesafe/jev-1.13",
  "state": "My invoice shows two charges for Pro plan.",
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "Which team handles this?",
      "criteria": {
        "billing": "Charges, invoices, refunds",
        "technical": "Bugs, outages, features"
      }
    }
  }
}
```

응답은 질문 이름을 키로 하며, 유형별 필드(선택 결과, 확률, 신뢰도)가 포함됩니다. 설명이나 추론 과정은 반환하지 않습니다.

---

## 적합한 용도

- **라우팅·분류**: 티켓 큐 배정, 의도 탐지, 크롤링한 페이지 분류
- **에이전트 게이팅**: 삭제·결제 같은 도구 호출 전에 되돌릴 수 있는지, 작업과 일치하는지 확인
- **검증**: 프롬프트 인젝션 탐지, 가드레일 검사, LLM 심사(judge)를 대체하는 기준 점수 매기기
- **랭킹·필터링**: RAG 후보 구절의 관련도를 점수화하고, 임계값은 코드에서 적용
- **신뢰도 기반 분기**: 신뢰도가 높으면 자동 처리하고, 낮으면 사람이나 추론 모델로 전달

---

## 한계와 주의점

- 답은 선택지 안에서만 나옵니다. 산문, 설명, 다단계 추론, 계획, 도구 호출은 할 수 없습니다.
- Jev는 텍스트만 입력받습니다. 이미지, 오디오, 영상은 처리하지 못합니다.
- 정확한 산술, 날짜 계산, 임계값 비교처럼 결정론적 로직은 정규식이나 DB 조회가 더 적합합니다.
- Noul 값이 0.5 근처이면 이진 신호가 아니라 **불확실하다는 신호**로 해석해야 합니다.
- 확률은 모델이 보정을 목표로 학습한 값이므로, 운영 데이터로 임계값을 검증한 뒤 사용해야 합니다.
- 시장이 초기 단계이므로 가격, 스키마, 성능 수치가 바뀔 수 있습니다.

---

## 언제 쓰고 언제 쓰지 않나

| 상황                                           | 선택                     |
| ---------------------------------------------- | ------------------------ |
| 답이 enum, boolean, 순서형 점수로 표현됨       | 결정 모델                |
| 판단 근거나 설명 문장이 필요함                 | LLM                      |
| 다단계 추론이나 계획이 필요함                  | 추론 모델                |
| 규칙이 명확하고 결정론적임                     | 일반 코드(정규식, DB)    |
| 이미지 입력이 필요함                           | 이미지를 지원하는 모델   |
